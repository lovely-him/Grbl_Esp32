# WiFi STA 连接重试机制优化建议

## 文档信息
- **提交日期**: 2026-01-22
- **提交方**: 集成商/二次开发方
- **目标读者**: 激光机原厂技术团队
- **涉及模块**: `Grbl_Esp32/src/WebUI` 目录下的 WiFi 连接模块

---

## 一、问题背景

在实际部署和测试过程中，我们发现 Grbl_Esp32 固件的 WiFi STA 模式连接存在**稳定性问题**：

### 1.1 现象描述
- WiFi 连接**偶尔会失败**，尤其是在以下场景：
  - 路由器信号较弱或不稳定时
  - 路由器负载较高时（多设备同时连接）
  - 设备刚上电，路由器尚未完全准备好时
  - 环境中存在 WiFi 干扰时

### 1.2 原有代码的局限性
经过代码审查，我们发现原有实现存在以下问题：

1. **单次尝试，无重试机制**
   - `StartSTA()` 函数只调用一次 `WiFi.begin()`
   - 如果首次连接失败，直接切换到 AP 模式
   - 没有给 WiFi 模块第二次机会

2. **超时时间硬编码**
   - `ConnectSTA2AP()` 中固定等待 20 秒（40 次迭代 × 500ms）
   - 无法根据实际网络环境调整
   - 用户无法通过配置修改

3. **错误处理不够灵活**
   - 检测到某些错误状态后立即退出
   - 没有考虑网络状态可能恢复的情况

### 1.3 实际影响
- **用户体验差**: 偶尔需要手动重启设备才能连接 WiFi
- **生产测试困难**: 批量测试时连接成功率不稳定
- **售后成本高**: 用户反馈"WiFi 连不上"的问题

---

## 二、优化方案

我们对 WiFi 连接逻辑进行了重构，核心思路是：**增加重试机制 + 可配置参数**。

### 2.1 修改的文件清单

| 文件 | 修改内容 |
|------|---------|
| `WifiConfig.h` | 新增重试次数和超时时间的常量定义 |
| `WifiConfig.cpp` | 重构 `StartSTA()` 和 `ConnectSTA2AP()` 函数 |
| `WebSettings.h` | 新增两个配置项的外部声明 |
| `WebSettings.cpp` | 新增两个 Web UI 可配置的设置项 |

### 2.2 核心改进点

#### 改进 1: 添加重试机制

**原有逻辑**:
```cpp
bool WiFiConfig::StartSTA() {
    if (WiFi.begin(SSID.c_str(), ...)) {
        return ConnectSTA2AP();  // 单次尝试
    } else {
        return false;
    }
}
```

**优化后逻辑**:
```cpp
bool WiFiConfig::StartSTA() {
    int32_t retry_count = wifi_sta_retry_count->get();  // 可配置重试次数

    for (int32_t attempt = 1; attempt <= retry_count; attempt++) {
        // 清理之前的连接状态
        wifi_services.end();
        WiFi.disconnect(true);

        // 显示当前尝试次数
        grbl_sendf(CLIENT_ALL, "[MSG:Connecting %s (attempt %d/%d)]\r\n",
                   SSID.c_str(), attempt, retry_count);

        // 尝试连接
        if (WiF(SSID.c_str(), ...)) {
            if (ConnectSTA2AP()) {
                return true;  // 连接成功
            }
        }

        // 断开连接，准备下次重试
        WiFi.disconnect();

        // 如果不是最后一次，等待后重试
        if (attempt < retry_count) {
            grbl_send(CLIENT_ALL, "[MSG:Retrying in 3 second...]\r\n");
            COMMANDS::wait(2800);  // 重试间隔
        }
    }

    return false;  // 所有重试都失败
}
```

**关键改进**:
- 支持多次重试（默认 3 次，可配置 1-10 次）
- 每次重试前清理 WiFi 状态，避免状态残留
- 显示当前重试进度，方便用户和技术人员诊断
- 重试间隔约 2.8 秒（可根据实际情况调整）

#### 改进 2: 可配置的超时时间

**原有逻辑**:
```cpp
bool WiFiConfig::ConnectSTA2AP() {
    uint8_t count = 0;
    while (status != WL_CONNECTED && count < 40) {  // 硬编码 40 次
        COMMANDS::wait(500);
        count++;
    }
}
```

**优化后逻辑**:
```cpp
bool WiFiConfig::ConnectSTA2AP() {
    int32_t timeout_ms = wifi_sta_connect_timeout->get();  // 可配置超时
    int32_t wait_interval_ms = 500;
    int32_t max_iterations = timeout_ms / wait_interval_ms;

    for (int32_t i = 0; i < max_iterations; i++) {
        wl_status_t status = WiFi.status();

        if (status == WL_CONNECTED) {
            return true;  // 连接成功
        }

        // 显示进度
        grbl_sendf(CLIENT_ALL, "[MSG:Connecting...]\r\n");
        COMMANDS::wait(wait_interval_ms);
    }

    grbl_send(CLIENT_ALL, "[MSG:Connection timeout]\r\n");
    return false;
}
```

**关键改进**:
- 超时时间可配置（默认 10 秒，范围 10-300 秒）
- 用户可根据实际网络环境调整
- 更清晰的超时提示消息

#### 改进 3: 灵活的错误处理

**设计考虑**:
- 某些 WiFi 错误状态（如 `WL_NO_SSID_AVAIL`、`WL_CONNECT_FAILED`）可能是**暂时性的**
- 路由器可能在短时间内恢复
- 因此我们选择**记录错误但继续等待**，而不是立即退出

```cpp
if (status == WL_NO_SSID_AVAIL) {
    grbl_send(CLIENT_ALL, "[MSG:No SSID available]\r\n");
    // 不立即返回 false，继续等待
}
if (status == WL_CONNECT_FAILED) {
    grbl_send(CLIENT_ALL, "[MSG:Connection failed]\r\n");
    // 不立即返回 false，继续等待
}
```

**理由**:
- 给网络状态恢复的机会
- 避免因瞬时错误导致连接失败
- 如果真的无法连接，超时机制会兜底

### 2.3 新增的配置项

我们在 Web UI 中新增了两个可配置参数：

| 配置项 | 默认值 | 范围 | 说明 |
|--------|--------|------|------|
| **Station Retry Count** | 3 次 | 1-10 次 | WiFi STA 连接失败时的重试次数 |
| **Station Connect Timeout** | 10000 ms | 10000-300000 ms | 单次连接尝试的超时时间 |

**配置路径**:
- Web UI: `Settings` → `WiFi` → `Station Retry Count` / `Station Connect Timeout`
- 配置文件: `Sta/RetryCount` / `Sta/ConnectTimeout`

## 三、初步测试观察

### 3.1 我们的测试环境
- **设备**: Wainlux K11 激光雕刻机（ESP32 控制器）
- **测试范围**: 有限的实验室环境测试
- **主观观察**: 添加重试机制后，WiFi 连接的稳定性有明显改善

### 3.2 观察到的改进
- 原有代码偶尔会出现连接失败，需要手动重启设备
- 添加重试机制后，这种情况明显减少
- 在信号不稳定的环境下，重试机制能够提高连接成功率

### 3.3 建议原厂进行的测试

**我们的测试环境和数据有限，强烈建议原厂在以下场景进行系统性测试**：

1. **多种路由器型号测试**
   - 不同品牌：TP-Link, 小米, 华硕, Netgear, 华为等
   - 不同频段：2.4GHz, 5GHz（如果支持）
   - 不同加密方式：WPA2, WPA3

2. **不同信号强度测试**
   - 强信号环境（-50 dBm 左右）
   - 中等信号（-70 dBm 左右）
   - 弱信号环境（-85 dBm 左右）
   - 建议统计每种场景下的连接成功率

3. **不同网络负载测试**
   - 路由器空闲状态
   - 路由器高负载（10+ 设备同时连接）
   - 路由器带宽占用较高时

4. **边界条件测试**
   - 设备冷启动时的连接成功率
   - 路由器重启时设备尝试连接的表现
   - SSID 不存在或密码错误时的行为
   - 长时间运行后的稳定性

5. **性能指标建议**
   - 统计各场景下的连接成功率
   - 记录平均连接时间
   - 测试总等待时间是否可接受
   - 评估用户体验影响

**我们期待原厂能够提供更全面的测试数据，以验证和优化这套重试机制。**

## 四、建议原厂采纳的理由

### 4.1 技术层面
1. **向后兼容**:
   - 默认参数（3 次重试，10 秒超时）适用于大多数场景
   - 不影响现有用户的使用习惯

2. **灵活性高**:
   - 用户可根据实际网络环境调整参数
   - 支持从 Web UI 动态配置，无需重新编译固件

3. **代码质量**:
   - 遵循项目的代码规范（`CodingStyle.md`）
   - 添加了详细的注释和日志输出
   - 没有修改核心运动控制代码，风险可控

### 4.2 商业层面
1. **降低售后成本**: 减少"WiFi 连不上"的用户投诉
2. **提升产品竞争力**: 更稳定的 WiFi 连接是用户体验的重要组成部分
3. **生产效率提升**: 批量测试时连接更可靠

### 4.3 预期效果
- 理论上可以降低售后成本，减少"WiFi 连不上"的用户投诉
- 提升用户对产品稳定性的信心
- 减少因连接问题导致的技术支持工作量

## 五、实施建议

### 5.1 代码审查要点
建议原厂技术团队重点审查以下方面：

1. **重试间隔时间**:
   - 我们当前使用的 2.8 秒是基于初步测试的经验值
   - **建议原厂根据实际测试数据调整**（可能 1-3 秒更合适）
   - 需要考虑 ESP32 WiFi 模块状态清理所需的时间

2. **默认参数**:
   - 重试次数默认 3 次（**仅供参考**，可考虑调整为 2-5 次）
   - 超时时间默认 10 秒（**仅供参考**，可考虑调整为 8-15 秒）
   - **这些参数需要原厂根据大量测试数据来确定最优值**

3. **错误处理策略**:
   - 我们选择在检测到 `WL_NO_SSID_AVAIL` 和 `WL_CONNECT_FAILED` 后继续等待
   - 理由是给网络状态恢复的机会
   - **但这个策略可能不是最优的**，如果原厂认为应该立即退出，可以取消注释 `return false;` 语句
   - 建议原厂根据实际测试结果决定最佳策略

4. **参数范围**:
   - 超时时间上限设为 300 秒（5 分钟）可能过长
   - 重试次数上限设为 10 次可能过多
   - **建议原厂根据实际需求调整这些边界值**

### 5.2 测试建议
建议原厂在以下场景进行充分测试：

1. **多种路由器型号**: TP-Link, 小米, 华硕, Netgear 等
2. **不同信号强度**: -50 dBm（强）, -70 dBm（中）, -85 dBm（弱）
3. **不同网络负载**: 路由器空闲 vs 高负载
4. **边界条件**:
   - 路由器重启时设备尝试连接
   - 设备冷启动时路由器尚未完全启动
   - SSID 不存在或密码错误

## 六、附录：参数调优参考

### 6.1 参考配置（仅供参考）

以下配置仅基于我们有限的测试经验，**实际最优值需要原厂通过系统性测试确定**：

| 场景 | 重试次数 | 单次超时 | 总等待时间 | 备注 |
|------|---------|---------|-----------|------|
| **正常网络** | 2 次 | 8 秒 | ~19 秒 | 可能适合大多数场景 |
| **弱信号环境** | 5 次 | 15 秒 | ~86 秒 | 需要更长等待时间 |
| **生产测试** | 3 次 | 10 秒 | ~36 秒 | 平衡成功率和效率 |
| **快速失败** | 1 次 | 5 秒 | 5 秒 | 快速检测连接问题 |

**注意**: 这些数值仅供参考，原厂应根据实际测试数据调整。

### 6.2 参数计算公式

```
总等待时间 = (单次超时 × 重试次数) + (重试间隔 × (重试次数 - 1))
```

示例（当前默认配置）:
```
总等待时间 = (10秒 × 3) + (2.8秒 × 2) = 35.6 秒
```

### 6.3 调优思路建议

1. **如果连接成功率已经很高（>95%）**:
   - 可以考虑减少重试次数（如 2 次）
   - 缩短单次超时（如 8 秒）
   - 目标：减少总等待时间，提升用户体验

2. **如果连接成功率较低（<90%）**:
   - 可以考虑增加重试次数（如 5 次）
   - 延长单次超时（如 15 秒）
   - 目标：提高连接成功率

3. **如果需要快速失败（如生产测试）**:
   - 设置重试次数为 1 次
   - 设置超时为 5-8 秒
   - 目标：快速检测连接问题

**重要提示**: 以上仅为调优思路，具体参数需要原厂根据大量实际测试数据来确定。
