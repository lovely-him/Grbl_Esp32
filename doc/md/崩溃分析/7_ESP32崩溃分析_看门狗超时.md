## 2. 异常类型

**WDT Timeout (Watchdog Timer Timeout)**

**定义**：
- 看门狗定时器超时，表示 IDLE 任务在规定时间内（通常 5 秒）无法运行
- 这是一种软件异常，由系统检测到任务调度异常时触发

---

## 3. 关键事实

### 3.1 崩溃时的系统状态

| 项目 | 值 |
|------|-----|
| **异常类型** | WDT Timeout |
| **未喂狗任务** | IDLE0 (CPU 0) |
| **CPU 0 运行任务** | wifi |
| **CPU 1 运行任务** | loopTask |
| **崩溃时间** | 362174 ms (系统运行约 6 分钟) |
| **崩溃地址** | 0x400feeb8 (task_wdt_isr) |

### 3.2 任务分配情况

**自定义任务配置** (来自 wainlux_k11_HIM.cpp:1055-1057):
```cpp
xTaskCreatePinnedToCore(led_fan_control_task, "LEDFan", 4096, NULL, 1, NULL, 1);  // CPU 1
xTaskCreatePinnedToCore(button_monitor_task, "Button", 4096, NULL, 1, NULL, 1);   // CPU 1
xTaskCreatePinnedToCore(safety_monitor_task, "Safety", 4096, NULL, 1, NULL, 1);   // CPU 1
```

**事实**：
- 所有自定义任务（Button, Safety, LED+Fan）都固定在 CPU 1
- WiFi 任务运行在 CPU 0
- 看门狗超时发生在 CPU 0

### 3.3 崩溃前的系统活动

**时间线**（基于日志）：
```
T-5s:  系统完成自动归零，状态从 Homing 转换到 Idle
T-1s:  I2C 总线状态检查警告 (SDA=0, SCL=1)
T0:    看门狗超时触发，系统 abort
```

**I2C 警告**：
```
[W][esp32-hal-i2c.c:1411] i2cCheckLineState(): invalid state sda(22)=0, scl(4)=1
```
- 出现在崩溃前约 1 秒
- I2C 操作在 safety_monitor_task 中，该任务运行在 CPU 1
- 看门狗超时在 CPU 0
- **两者在不同核心上**

### 4.3 调用链说明

**WiFi 任务执行路径**：
```
ppTask (WiFi 物理层任务)
  → wdevProcessRxSucDataAll (处理接收数据)
    → lmacRxDone (MAC 层接收完成)
      → pp_post (物理层后处理)
        → queue_send_wrapper (队列发送)
          → [看门狗中断触发]
```

**事实**：
- WiFi 任务正在执行正常的数据包处理流程
- 当看门狗中断触发时，WiFi 任务在 `queue_send_wrapper` 函数中
- 这是 WiFi 驱动的内部操作，不是应用层代码

## 5. 已知事实总结

### 5.1 确定的事实

1. **IDLE0 任务无法运行**
   - IDLE0 (CPU 0) 在 5 秒内未能运行
   - 触发看门狗超时

2. **WiFi 任务占用 CPU 0**
   - 看门狗触发时，WiFi 任务正在 CPU 0 上运行
   - WiFi 任务在处理接收的数据包

3. **任务分配**
   - 自定义任务（包括 I2C 操作）在 CPU 1
   - WiFi 任务在 CPU 0
   - 两个核心的任务相互独立

4. **系统状态**
   - 系统刚完成归零，进入 Idle 状态
   - WiFi 已连接 (192.168.137.46)
   - 所有网络服务已启动

### 5.2 未知的问题

1. **为什么 IDLE0 无法运行？**
   - 日志中没有直接证据说明原因
   - 需要更多运行时信息

2. **WiFi 任务为什么持续占用 CPU？**
   - 调用栈显示正常操作
   - 无法从日志判断是否异常

3. **I2C 警告是否相关？**
   - 时间上接近，但在不同核心
   - 无法确定因果关系
