## 1.1 崩溃日志结构

ESP32 崩溃日志通常包含以下 4 个核心部分：

### 1.1.1 典型结构

```
┌─────────────────────────────────────────────────────────┐
│ 1. 异常头部 (Exception Header)                          │
│    Guru Meditation Error: Core X panic'ed (异常类型)    │
├─────────────────────────────────────────────────────────┤
│ 2. 寄存器转储 (Register Dump)                           │
│    PC, EXCVADDR, EXCCAUSE, A0-A15, SAR, LBEG, LEND...  │
├─────────────────────────────────────────────────────────┤
│ 3. 调用栈 (Backtrace)                                   │
│    Backtrace: 0x4xxxxxxx:0x3fxxxxxx ...                │
├─────────────────────────────────────────────────────────┤
│ 4. 内存状态 (Memory Status) [可选]                      │
│    Free heap, Min heap, MaxAlloc                       │
└─────────────────────────────────────────────────────────┘
```

### 1.1.2 完整示例

```
Guru Meditation Error: Core 0 panic'ed (LoadProhibited). Exception was unhandled.

Core 0 register dump:
PC      : 0x400d1234  PS      : 0x00060330  A0      : 0x800d5678  A1      : 0x3ffb1234
A2      : 0x00000000  A3      : 0x3ffb5678  A4      : 0x00000001  A5      : 0x3ffb9abc
A6      : 0x00000000  A7      : 0x00000000  A8      : 0x800d1234  A9      : 0x3ffb1200
A10     : 0x00000000  A11     : 0x3ffb5678  A12     : 0x00000000  A13     : 0x3ffb9abc
A14     : 0x00000000  A15     : 0x00000000  SAR     : 0x00000000  EXCCAUSE: 0x0000001c
EXCVADDR: 0x00000018  LBEG    : 0x4000c46c  LEND    : 0x4000c477  LCOUNT  : 0x00000000

Backtrace: 0x400d1234:0x3ffb1234 0x400d5678:0x3ffb1260 0x400d9abc:0x3ffb1290
```

### 1.1.3 各部分含义

| 部分 | 含义 | 关键信息 |
|------|------|---------|
| **异常头部** | 崩溃类型和核心 | 异常类型（LoadProhibited, StoreProhibited 等） |
| **寄存器转储** | CPU 寄存器状态 | PC（崩溃地址）、EXCVADDR（访问地址）、EXCCAUSE（异常代码） |
| **调用栈** | 函数调用链 | 地址对（PC:SP），从崩溃点到 main() |
| **内存状态** | 堆内存使用情况 | Free（可用）、Min（历史最低）、MaxAlloc（最大可分配） |

## 1.2 关键信息识别

**目标**: 在 1 分钟内提取 3 个最关键的信息。

### 1.2.1 三大关键信息

```
┌──────────────────────────────────────────────────────────┐
│ 1. 异常类型 (EXCCAUSE)                                   │
│    → 判断问题类别（内存/指令/对齐/中断）                  │
├──────────────────────────────────────────────────────────┤
│ 2. 崩溃地址 (PC / EXCVADDR)                              │
│    → 定位崩溃位置和访问的无效地址                         │
├──────────────────────────────────────────────────────────┤
│ 3. 调用栈 (Backtrace)                                    │
│    → 追溯函数调用链，找到触发路径                         │
└──────────────────────────────────────────────────────────┘
```

### 1.2.2 提取方法

#### 信息 1：异常类型

**位置**: 异常头部或 EXCCAUSE 寄存器

```
Guru Meditation Error: Core 0 panic'ed (LoadProhibited)
                                         ^^^^^^^^^^^^^^
                                         异常类型
```

或

```
EXCCAUSE: 0x0000001c
          ^^^^^^^^^^
          异常代码 → 查表得到类型
```

**速查**: 见 [3.3 EXCCAUSE 完整对照表](#33-exccause-完整对照表)

#### 信息 2：崩溃地址

**PC (Program Counter)**: 崩溃发生的指令地址

```
PC      : 0x400d1234
          ^^^^^^^^^^
          崩溃指令地址
```

**EXCVADDR (Exception Virtual Address)**: 访问的无效地址（仅内存访问异常）

```
EXCVADDR: 0x00000018
          ^^^^^^^^^^
          尝试访问的地址
```

**判断规则**:
- `EXCVADDR = 0x00000000` → 空指针解引用
- `EXCVADDR = 0x00000004 ~ 0x00000020` → 空指针偏移（访问成员变量）
- `EXCVADDR = 0x3fxxxxxx` → 访问已释放的堆内存
- `EXCVADDR = 0x4xxxxxxx` → 访问代码段（通常是函数指针错误）

#### 信息 3：调用栈

**位置**: Backtrace 行

```
Backtrace: 0x400d1234:0x3ffb1234 0x400d5678:0x3ffb1260 0x400d9abc:0x3ffb1290
           ^^^^^^^^^^  ^^^^^^^^^^
           PC 地址     SP 地址
```

**格式**: `PC:SP PC:SP ...`
- **PC**: 函数返回地址（调用者的下一条指令）
- **SP**: 栈指针（函数栈帧位置）

**解码**: 使用 `addr2line` 工具转换为源码位置，见 [2.3 命令语法速查](#23-命令语法速查)

### 1.2.3 快速提取命令

```bash
# 提取异常类型
grep "panic'ed" crash.log

# 提取寄存器（PC, EXCVADDR, EXCCAUSE）
grep -E "^(PC|EXCVADDR|EXCCAUSE)" crash.log

# 提取 Backtrace
grep "^Backtrace:" crash.log
```

## 1.3 快速诊断流程

**目标**: 5 分钟内判断问题类型和严重程度。

### 1.3.1 诊断流程图

```
开始
  │
  ├─→ 提取异常类型 (EXCCAUSE)
  │     │
  │     ├─→ LoadProhibited (0x1c) ────→ 内存读取错误
  │     │     └─→ 检查 EXCVADDR
  │     │           ├─→ 0x00000000 ~ 0x00000020 → 空指针/野指针
  │     │           ├─→ 0x3fxxxxxx → 访问已释放内存
  │     │           └─→ 其他 → 访问无效地址
  │     │
  │     ├─→ StoreProhibited (0x1d) ───→ 内存写入错误
  │     │     └─→ 检查 EXCVADDR（同上）
  │     │
  │     ├─→ LoadStoreAlignment (0x09) → 内存对齐错误
  │     │     └─→ 检查 EXCVADDR 是否对齐
  │     │
  │     ├─→ IllegalInstruction (0x00) → 非法指令
  │     │     └─→ 检查 PC 地址是否有效
  │     │
  │     ├─→ InstrFetchProhibited (0x14) → 指令获取错误
  │     │     └─→ 检查 PC 地址是否可执行
  │     │
  │     ├─→ IntegerDivideByZero (0x06) → 除零错误
  │     │     └─→ 检查调用栈中的除法操作
  │     │
  │     └─→ 其他 → 查表 [3.3 节](#33-exccause-完整对照表)
  │
  ├─→ 解码 Backtrace
  │     └─→ 使用 addr2line 转换为源码位置
  │           └─→ 识别崩溃函数和调用链
  │
  ├─→ 检查内存状态（如果有）
  │     ├─→ Free < 10KB → 内存耗尽
  │     ├─→ MaxAlloc << Free → 内存碎片化
  │     └─→ Min 接近 0 → 历史内存压力
  │
  └─→ 匹配崩溃模式
        └─→ 使用 [5.4 模式识别决策树](#54-模式识别决策树)
              └─→ 确定问题类型和排查方向
```

### 1.3.2 快速判断表

| 特征 | 可能原因 | 下一步 |
|------|---------|--------|
| **EXCVADDR = 0x00000000** | 空指针解引用 | 检查调用栈中的指针操作 |
| **EXCVADDR = 0x00000004 ~ 0x00000020** | 空指针偏移（成员变量） | 检查对象生命周期 |
| **EXCVADDR = 0x3fxxxxxx** | 访问已释放内存 | 检查内存释放和使用顺序 |
| **Free < 10KB** | 内存耗尽 | 检查内存分配和泄漏 |
| **MaxAlloc << Free** | 内存碎片化 | 优化内存分配策略 |
| **调用栈包含 `new[]` / `malloc`** | 内存分配失败 | 添加异常处理 |
| **调用栈包含定时器回调** | 定时器生命周期问题 | 检查定时器停止逻辑 |
| **调用栈包含中断处理** | 中断上下文错误 | 检查中断安全性 |

### 1.3.3 严重程度评估

| 级别 | 特征 | 影响 | 优先级 |
|------|------|------|--------|
| **P0 - 致命** | 系统崩溃重启 | 业务完全中断 | 立即修复 |
| **P1 - 严重** | 功能失效但不崩溃 | 核心功能不可用 | 24 小时内修复 |
| **P2 - 中等** | 偶发崩溃 | 部分功能受影响 | 1 周内修复 |
| **P3 - 轻微** | 日志错误但无崩溃 | 用户体验下降 | 下个版本修复 |

### 1.3.4 快速诊断检查清单

```
□ 提取异常类型（EXCCAUSE 或异常头部）
□ 提取崩溃地址（PC 和 EXCVADDR）
□ 提取调用栈（Backtrace）
□ 解码 Backtrace 为源码位置
□ 检查内存状态（Free, Min, MaxAlloc）
□ 匹配崩溃模式（使用决策树）
□ 评估严重程度（P0-P3）
□ 确定排查方向（内存/并发/外设）
```

### 1.3.5 示例：5 分钟快速诊断

**输入**: 崩溃日志

```
Guru Meditation Error: Core 0 panic'ed (LoadProhibited). Exception was unhandled.
PC      : 0x400d1234  EXCVADDR: 0x00000018  EXCCAUSE: 0x0000001c
Backtrace: 0x400d1234:0x3ffb1234 0x400d5678:0x3ffb1260
```

**步骤 1**: 提取关键信息（30 秒）
- 异常类型: `LoadProhibited` (0x1c)
- 崩溃地址: PC = `0x400d1234`, EXCVADDR = `0x00000018`
- 调用栈: `0x400d1234`, `0x400d5678`

**步骤 2**: 解码 Backtrace（2 分钟）
```bash
addr2line -pfiaC -e firmware.elf 0x400d1234 0x400d5678
# 输出:
# 0x400d1234: SSDPClass::_onTimerStatic() at ESP32SSDP.cpp:456
# 0x400d5678: timer_callback() at esp_timer.c:123
```

**步骤 3**: 分析（2 分钟）
- **EXCVADDR = 0x18**: 空指针偏移，访问对象成员变量（偏移 24 字节）
- **调用栈**: 定时器回调 → SSDP 类方法
- **判断**: 定时器回调访问已销毁对象

**步骤 4**: 匹配模式（30 秒）
- 模式: [5.2.3 定时器生命周期问题](#523-定时器生命周期问题)
- 原因: 定时器停止后回调仍执行

**结论**: P0 级别，定时器竞态条件，需立即修复。

**下一步**: 参考 [第四部分](#第四部分标准分析流程) 进行详细分析。

### 2.3.1 addr2line 基本用法

### 2.3.2 解码 Backtrace


```bash
xtensa-esp32-elf-addr2line -pfiaC \
```

## 2.4 常见问题 FAQ

### 2.4.1 工具找不到

**问题**: `xtensa-esp32-elf-addr2line: command not found`

**解决方案**:
```bash
# 方法 1: 使用完整路径
~/.platformio/packages/toolchain-xtensa32/bin/xtensa-esp32-elf-addr2line

# 方法 2: 添加到 PATH
export PATH="$HOME/.platformio/packages/toolchain-xtensa32/bin:$PATH"

# 方法 3: 创建别名
alias addr2line='~/.platformio/packages/toolchain-xtensa32/bin/xtensa-esp32-elf-addr2line'
```

### 2.4.2 ELF 文件找不到

**问题**: `firmware.elf: No such file or directory`

**解决方案**:
```bash
# 检查 ELF 文件位置
find . -name "firmware.elf"

# PlatformIO 默认位置
.pio/build/<环境名>/firmware.elf

# Arduino IDE 默认位置（Windows）
C:\Users\<用户名>\AppData\Local\Temp\arduino_build_<随机数>\<项目名>.ino.elf

# 确保已编译项目
pio run  # PlatformIO
```

### 2.4.3 解码结果显示 ??

**问题**: 解码输出 `??:0` 或 `??:?`

**原因**:
1. ELF 文件与固件不匹配（重新编译后未更新 ELF）
2. 地址不在代码段（可能是数据地址）
3. 优化导致调试信息丢失

**解决方案**:
```bash
# 1. 确保 ELF 文件是最新的
pio run  # 重新编译

# 2. 检查编译选项（platformio.ini）
build_flags =
    -DCORE_DEBUG_LEVEL=5
    -g                    # 生成调试信息
    -O0                   # 禁用优化（可选）

# 3. 检查地址是否有效
# 有效代码地址范围: 0x40000000 ~ 0x400FFFFF (IRAM)
#                   0x400D0000 ~ 0x40400000 (Flash)
```

### 2.4.4 Backtrace 地址格式错误

**问题**: Backtrace 包含 `0x8xxxxxxx` 地址

**原因**: 这是返回地址（A0 寄存器），需要转换

**解决方案**:
```bash
# 0x8xxxxxxx 地址需要减 3 并清除最高位
# 例如: 0x800d5678 → 0x400d5675

# 自动转换（Linux/macOS）
echo "0x800d5678" | awk '{printf "0x%08x\n", (strtonum($1) - 3) & 0x3FFFFFFF}'

# 手动计算
0x800d5678 - 3 = 0x800d5675
0x800d5675 & 0x3FFFFFFF = 0x000d5675
0x000d5675 | 0x40000000 = 0x400d5675
```

### 2.4.5 PlatformIO 解码不工作

**问题**: `monitor_filters = esp32_exception_decoder` 不生效

**解决方案**:
```bash
# 1. 检查 PlatformIO 版本
pio --version  # 需要 >= 5.0

# 2. 更新 PlatformIO
pio upgrade

# 3. 清理并重新编译
pio run --target clean
pio run

# 4. 手动指定 filter
pio device monitor --filter esp32_exception_decoder

# 5. 检查 ELF 文件路径
# PlatformIO 自动查找 .pio/build/<env>/firmware.elf
```

### 2.4.6 VSCode 扩展无法解码

**问题**: VSCode ESP Exception Decoder 扩展不工作

**解决方案**:
```bash
# 1. 检查扩展是否安装
code --list-extensions | grep esp-exception-decoder

# 2. 配置 ELF 文件路径（.vscode/settings.json）
{
    "esp-exception-decoder.elfPath": "${workspaceFolder}/.pio/build/release/firmware.elf"
}

# 3. 重启 VSCode
```

### 2.4.7 Core Dump 无法读取

**问题**: `esp-coredump.py` 报错 `Invalid core dump`

**解决方案**:
```bash
# 1. 检查 Core Dump 配置（sdkconfig）
CONFIG_ESP32_ENABLE_COREDUMP=y
CONFIG_ESP32_ENABLE_COREDUMP_TO_FLASH=y

# 2. 检查分区表是否包含 coredump 分区
pio run --target menuconfig
# Component config → Core dump → Data destination → Flash

# 3. 读取 Core Dump
esptool.py --port /dev/ttyUSB0 read_flash 0x3F0000 0x10000 coredump.bin

# 4. 解码
esp-coredump.py info_corefile -t raw -c coredump.bin firmware.elf
```

### 2.4.8 GDB 无法连接

**问题**: `target remote :3333` 失败

**解决方案**:
```bash
# 1. 检查 OpenOCD 是否运行
ps aux | grep openocd

# 2. 启动 OpenOCD
openocd -f interface/ftdi/esp32_devkitj_v1.cfg -f target/esp32.cfg

# 3. 检查端口
netstat -an | grep 3333

# 4. 使用正确的 GDB
xtensa-esp32-elf-gdb firmware.elf
```

### 2.4.9 符号解码失败 (C++)

**问题**: 函数名显示为 `_Z12functionNamev`

**原因**: 缺少 `-C` 选项（C++ demangle）

**解决方案**:
```bash
# 添加 -C 选项
xtensa-esp32-elf-addr2line -pfiaC -e firmware.elf 0x400d1234
```

### 2.4.10 内存地址无法解码

**问题**: 尝试解码 `0x3ffb1234` 等内存地址

**原因**: 这是栈地址（SP），不是代码地址（PC）

**解决方案**:
```bash
# Backtrace 格式: PC:SP
# 只解码 PC 部分（冒号前）
# 0x400d1234:0x3ffb1234 → 解码 0x400d1234
```

## 3.1 硬件异常表

### 3.1.1 内存访问异常

| EXCCAUSE | 异常类型 | 定义 | 可捕获 | 常见原因 |
|----------|---------|------|--------|---------|
| **0x1c** | **LoadProhibited** | 读取无效内存地址 | ❌ | 空指针、野指针、已释放内存 |
| **0x1d** | **StoreProhibited** | 写入无效内存地址 | ❌ | 空指针、野指针、已释放内存 |
| **0x09** | **LoadStoreAlignment** | 内存对齐错误 | ❌ | 未对齐的多字节访问 |
| **0x14** | **InstrFetchProhibited** | 指令获取错误 | ❌ | PC 指向无效地址 |

**特征识别**:
- **LoadProhibited**: `EXCVADDR` 指向尝试读取的地址
- **StoreProhibited**: `EXCVADDR` 指向尝试写入的地址
- **LoadStoreAlignment**: `EXCVADDR` 不是 2/4 字节对齐
- **InstrFetchProhibited**: `PC` 指向无效或不可执行地址

### 3.1.2 指令异常

| EXCCAUSE | 异常类型 | 定义 | 可捕获 | 常见原因 |
|----------|---------|------|--------|---------|
| **0x00** | **IllegalInstruction** | 非法指令 | ❌ | 代码损坏、PC 跳转错误 |
| **0x06** | **IntegerDivideByZero** | 整数除零 | ❌ | 除数为 0 |
| **0x02** | **InstructionFetchError** | 指令获取失败 | ❌ | Flash 读取错误 |

**特征识别**:
- **IllegalInstruction**: `PC` 指向的指令无效
- **IntegerDivideByZero**: 调用栈包含除法操作
- **InstructionFetchError**: Flash 或 IRAM 访问失败

### 3.1.3 中断异常

| EXCCAUSE | 异常类型 | 定义 | 可捕获 | 常见原因 |
|----------|---------|------|--------|---------|
| **0x04** | **Level1Interrupt** | 1 级中断 | ❌ | 中断处理错误 |
| **0x05** | **Alloca** | Alloca 异常 | ❌ | 栈分配失败 |
| **0x20** | **InstrPIF** | 指令 PIF 错误 | ❌ | 总线错误 |
| **0x28** | **LoadPIF** | 加载 PIF 错误 | ❌ | 总线错误 |
| **0x29** | **StorePIF** | 存储 PIF 错误 | ❌ | 总线错误 |

### 3.1.4 协处理器异常

| EXCCAUSE | 异常类型 | 定义 | 可捕获 | 常见原因 |
|----------|---------|------|--------|---------|
| **0x20** | **Coprocessor0Disabled** | 协处理器 0 禁用 | ❌ | 使用未启用的协处理器 |
| **0x24** | **Coprocessor1Disabled** | 协处理器 1 禁用 | ❌ | 使用未启用的协处理器 |

## 3.2 软件异常表

### 3.2.1 C++ 异常

| 异常类型 | 定义 | 可捕获 | 常见原因 | 调用栈特征 |
|---------|------|--------|---------|-----------|
| **std::bad_alloc** | 内存分配失败 | ✅ | 堆内存耗尽、碎片化 | `operator new[]`, `malloc` |
| **std::out_of_range** | 数组越界 | ✅ | 索引超出范围 | `std::vector::at`, `std::string::at` |
| **std::length_error** | 长度错误 | ✅ | 容器大小超限 | `std::vector::resize` |
| **std::runtime_error** | 运行时错误 | ✅ | 自定义运行时错误 | 用户代码 |
| **std::logic_error** | 逻辑错误 | ✅ | 自定义逻辑错误 | 用户代码 |

**识别特征**:
- 调用栈包含 `__cxa_throw`, `std::terminate`, `abort()`
- 日志显示 `abort() was called at PC 0xXXXXXXXX`
- 未捕获异常导致 `std::terminate()` 调用

### 3.2.2 断言失败

| 异常类型 | 定义 | 可捕获 | 常见原因 | 调用栈特征 |
|---------|------|--------|---------|-----------|
| **assert()** | 断言失败 | ❌ | 条件不满足 | `__assert_func`, `abort()` |
| **ESP_ERROR_CHECK()** | ESP-IDF 错误检查 | ❌ | 函数返回错误码 | `_esp_error_check_failed` |
| **configASSERT()** | FreeRTOS 断言 | ❌ | FreeRTOS 内部错误 | `vAssertCalled` |

**识别特征**:
- 日志显示 `assertion "条件" failed: file "文件", line 行号`
- 调用栈包含 `__assert_func` 或 `_esp_error_check_failed`

### 3.2.3 系统 Panic

| 异常类型 | 定义 | 可捕获 | 常见原因 | 调用栈特征 |
|---------|------|--------|---------|-----------|
| **abort()** | 主动终止 | ❌ | 未捕获异常、断言失败 | `abort`, `_exit` |
| **panic()** | 系统 Panic | ❌ | 严重错误 | `panic_abort`, `esp_panic_handler` |
| **WDT Timeout** | 看门狗超时 | ❌ | 任务阻塞、死循环 | `esp_task_wdt_isr` |

**识别特征**:
- **abort()**: 日志显示 `abort() was called at PC 0xXXXXXXXX`
- **panic()**: 日志显示 `Guru Meditation Error`
- **WDT**: 日志显示 `Task watchdog got triggered`

### 3.2.4 栈溢出

| 异常类型 | 定义 | 可捕获 | 常见原因 | 识别特征 |
|---------|------|--------|---------|---------|
| **Stack Overflow** | 栈空间耗尽 | ❌ | 递归过深、局部变量过大 | `***ERROR*** A stack overflow in task` |
| **Stack Canary** | 栈保护触发 | ❌ | 栈溢出破坏保护字 | `Stack canary watchpoint triggered` |

**识别特征**:
- 日志显示 `***ERROR*** A stack overflow in task <任务名>`
- 调用栈显示深度递归
- `SP` 寄存器接近栈底

## 3.4 异常分类决策树

### 3.4.1 根据 EXCCAUSE 分类

```
EXCCAUSE 值
  │
  ├─→ 0x1c (LoadProhibited)
  │     └─→ 内存读取错误
  │           ├─→ EXCVADDR = 0x00000000 → 空指针解引用
  │           ├─→ EXCVADDR = 0x00000004~0x00000020 → 空指针偏移
  │           ├─→ EXCVADDR = 0x3fxxxxxx → 访问已释放堆内存
  │           ├─→ EXCVADDR = 0x4xxxxxxx → 访问代码段（函数指针错误）
  │           └─→ 其他 → 访问无效地址
  │
  ├─→ 0x1d (StoreProhibited)
  │     └─→ 内存写入错误
  │           ├─→ EXCVADDR = 0x00000000 → 空指针解引用
  │           ├─→ EXCVADDR = 0x00000004~0x00000020 → 空指针偏移
  │           ├─→ EXCVADDR = 0x3fxxxxxx → 写入已释放堆内存
  │           └─→ 其他 → 写入无效地址
  │
  ├─→ 0x09 (LoadStoreAlignment)
  │     └─→ 内存对齐错误
  │           ├─→ EXCVADDR % 2 ≠ 0 → 16 位访问未对齐
  │           ├─→ EXCVADDR % 4 ≠ 0 → 32 位访问未对齐
  │           └─→ 检查结构体打包和类型转换
  │
  ├─→ 0x00 (IllegalInstruction)
  │     └─→ 非法指令
  │           ├─→ PC 在有效范围 → 代码损坏
  │           ├─→ PC 在无效范围 → 函数指针错误
  │           └─→ 检查 Flash 完整性
  │
  ├─→ 0x06 (IntegerDivideByZero)
  │     └─→ 除零错误
  │           └─→ 检查调用栈中的除法操作
  │
  ├─→ 0x14 (InstrFetchProhibited)
  │     └─→ 指令获取错误
  │           ├─→ PC = 0x00000000 → 空函数指针
  │           ├─→ PC 在数据段 → 函数指针指向数据
  │           └─→ PC 无效 → 栈损坏或返回地址错误
  │
  └─→ 其他
        └─→ 查表 [3.3 节](#33-exccause-完整对照表)
```

### 3.4.2 根据调用栈特征分类

```
调用栈包含
  │
  ├─→ operator new[] / malloc
  │     └─→ 内存分配失败
  │           ├─→ 检查 Free heap
  │           ├─→ 检查 MaxAlloc
  │           └─→ 参考 [5.1.1 堆内存耗尽](#511-堆内存耗尽)
  │
  ├─→ __cxa_throw / std::terminate
  │     └─→ 未捕获 C++ 异常
  │           ├─→ 检查异常类型（std::bad_alloc, std::out_of_range）
  │           └─→ 参考 [3.2.1 C++ 异常](#321-c-异常)
  │
  ├─→ __assert_func / _esp_error_check_failed
  │     └─→ 断言失败
  │           ├─→ 检查日志中的断言条件
  │           └─→ 参考 [3.2.2 断言失败](#322-断言失败)
  │
  ├─→ timer_callback / ets_timer_*
  │     └─→ 定时器相关
  │           ├─→ 检查定时器生命周期

```

### 3.4.3 根据内存状态分类

```
内存状态
  │
  ├─→ Free < 10KB
  │     └─→ 内存严重不足
  │           ├─→ 检查内存泄漏

  │           ├─→ 检查频繁的小块分配/释放

  │           └─→ 增加堆内存预留

  └─→ Free 充足但仍崩溃

```

## 4.2 步骤 1：提取关键信息

**目标**: 从崩溃日志中提取 3 个最关键的信息（参考 [1.2 节](#12-关键信息识别)）。

### 4.2.1 提取检查清单

```
□ 异常类型 (EXCCAUSE 或异常头部)
□ 崩溃地址 (PC)
□ 访问地址 (EXCVADDR，如果有)
□ 调用栈 (Backtrace)
□ 内存状态 (Free, Min, MaxAlloc，如果有)
□ 崩溃时间和上下文
```

### 4.2.2 提取命令

```bash
# 提取异常头部

# 提取寄存器
grep -E "^(PC|EXCVADDR|EXCCAUSE)" crash.log

# 提取 Backtrace
grep "^Backtrace:" crash.log

# 提取内存状态
grep -E "(Free|Min|MaxAlloc)" crash.log | tail -5

# 提取崩溃前后的日志（前后各 10 行）
grep -B10 -A10 "panic'ed" crash.log
```

### 4.2.3 通用示例

**输入**: 崩溃日志片段

```
[14:32:40.197] Guru Meditation Error: Core 0 panic'ed (LoadProhibited). Exception was unhandled.

Core 0 register dump:

EXCVADDR: 0x00000018  EXCCAUSE: 0x0000001c

```

**输出**: 关键信息表

| 项目 | 值 | 含义 |
|------|-----|------|
| **异常类型** | LoadProhibited (0x1c) | 读取无效内存地址 |
| **崩溃地址 (PC)** | 0x400ef123 | 崩溃指令位置 |
| **访问地址 (EXCVADDR)** | 0x00000018 | 尝试读取的地址（空指针偏移 24 字节） |
| **调用栈** | 0x400ef123, 0x400f5675, 0x400f9abc | 3 层调用 |
| **核心** | Core 0 | 主核心 |

## 4.3 步骤 2：解码 Backtrace

**目标**: 将地址转换为源码位置（参考 [2.3 节](#23-命令语法速查)）。

### 4.3.1 解码步骤

```
1. 提取 PC 地址（冒号前的部分）
2. 处理 0x8xxxxxxx 地址（减 3 并转换）
3. 使用 addr2line 解码
4. 记录函数名、文件名、行号
```

### 4.3.2 解码命令

**基本解码**:
```bash
xtensa-esp32-elf-addr2line -pfiaC \
  -e .pio/build/release/firmware.elf \
  0x400ef123 0x400f5675 0x400f9abc
```

**处理 0x8xxxxxxx 地址**:
```bash
# 0x800f5678 → 0x400f5675
# 公式: (地址 - 3) & 0x3FFFFFFF | 0x40000000

# Linux/macOS 自动转换
echo "0x800f5678" | awk '{printf "0x%08x\n", (strtonum($1) - 3) & 0x3FFFFFFF | 0x40000000}'
```

### 4.3.3 通用示例

**输入**: Backtrace 地址

```
0x400ef123 0x400f5675 0x400f9abc
```

**解码输出**:

```
0x400f5675: timer_callback_wrapper at components/esp_timer/src/esp_timer.c:123
0x400f9abc: timer_task at components/esp_timer/src/esp_timer.c:456
```

**格式化为表格**:

| 地址 | 函数 | 文件 | 行号 |
|------|------|------|------|
| 0x400ef123 | MyClass::processData() | src/MyClass.cpp | 456 |
| 0x400f5675 | timer_callback_wrapper | esp_timer.c | 123 |
| 0x400f9abc | timer_task | esp_timer.c | 456 |

## 4.4 步骤 3：分析寄存器

**目标**: 理解寄存器值的含义，特别是 PC、EXCVADDR、A0-A15。

### 4.4.1 关键寄存器

| 寄存器 | 含义 | 分析要点 |
|--------|------|---------|
| **PC** | 程序计数器 | 崩溃指令地址，解码后得到崩溃函数 |
| **EXCVADDR** | 异常虚拟地址 | 尝试访问的内存地址（仅内存异常） |
| **EXCCAUSE** | 异常原因代码 | 异常类型，查表 [3.3 节](#33-exccause-完整对照表) |
| **A0** | 返回地址 | 调用者的返回地址（通常是 0x8xxxxxxx） |
| **A1 (SP)** | 栈指针 | 当前栈帧位置 |
| **A2-A7** | 函数参数/局部变量 | 函数调用时的参数 |
| **A8-A15** | 保存的寄存器 | 调用者保存的寄存器值 |

### 4.4.2 EXCVADDR 分析

**判断规则**:

| EXCVADDR 范围 | 含义 | 可能原因 |
|--------------|------|---------|
| **0x00000000** | 空指针 | 直接解引用 NULL |
| **0x00000004 ~ 0x00000020** | 空指针偏移 | 访问 NULL 对象的成员变量 |
| **0x3f400000 ~ 0x3f800000** | DRAM (堆/栈) | 访问已释放的堆内存或栈溢出 |
| **0x3ff00000 ~ 0x3fffffff** | DRAM (外设) | 访问外设寄存器（可能未初始化） |
| **0x40000000 ~ 0x400fffff** | IRAM | 访问代码段（函数指针错误） |
| **0x40100000 ~ 0x40400000** | Flash | 访问 Flash 代码段（函数指针错误） |
| **其他** | 无效地址 | 野指针或地址计算错误 |

### 4.4.3 通用示例

**输入**: 寄存器转储

```
PC      : 0x400ef123  PS      : 0x00060330  A0      : 0x800f5678  A1      : 0x3ffb7890
A2      : 0x00000000  A3      : 0x3ffb5678  A4      : 0x00000001  A5      : 0x3ffb9abc
EXCVADDR: 0x00000018  EXCCAUSE: 0x0000001c
```

**分析**:

| 寄存器 | 值 | 分析 |
|--------|-----|------|
| **PC** | 0x400ef123 | 崩溃指令地址 → MyClass::processData() at MyClass.cpp:456 |
| **EXCVADDR** | 0x00000018 | 空指针偏移 24 字节 → 访问对象成员变量（偏移 0x18） |
| **EXCCAUSE** | 0x1c | LoadProhibited → 读取无效内存 |
| **A0** | 0x800f5678 | 返回地址 → timer_callback_wrapper() |
| **A1 (SP)** | 0x3ffb7890 | 栈指针 → 栈帧位置正常 |
| **A2** | 0x00000000 | 第一个参数 → **NULL 指针**（this 指针） |
| **A3** | 0x3ffb5678 | 第二个参数 → 有效堆地址 |

**结论**:
- **this 指针为 NULL** (A2 = 0x00000000)
- 尝试访问成员变量（偏移 0x18）
- 在定时器回调中调用（A0 指向 timer_callback_wrapper）
- **根本原因**: 定时器回调访问已销毁的对象

---

## 4.5 步骤 4：诊断内存状态

**目标**: 评估内存使用情况，判断是否存在内存问题。

### 4.5.1 内存指标含义

| 指标 | 含义 | 正常范围 | 警告阈值 |
|------|------|---------|---------|
| **Free** | 当前可用堆内存 | > 50KB | < 20KB |
| **Min** | 历史最低可用内存 | > 30KB | < 10KB |
| **MaxAlloc** | 最大可分配连续块 | 接近 Free | < Free/2 |

### 4.5.2 诊断规则

```
内存状态判断
  │
  ├─→ Free < 10KB
  │     └─→ 内存严重不足
  │           → 检查内存泄漏和大块分配
  │
  ├─→ MaxAlloc < Free / 2
  │     └─→ 内存碎片化严重
  │           → 优化内存分配策略
  │
  ├─→ Min < 10KB
  │     └─→ 历史内存压力
  │           → 增加堆内存预留
  │
  └─→ Free 充足但仍崩溃
        └─→ 非内存不足问题
              → 检查指针有效性和并发安全
```

### 4.5.3 通用示例

**输入**: 内存日志

```
[14:32:39.589] Memory: Free=38424, Min=21088, MaxAlloc=20444 bytes
[14:32:40.197] Guru Meditation Error: Core 0 panic'ed (LoadProhibited)
```

**分析**:

| 指标 | 值 | 评估 | 结论 |
|------|-----|------|------|
| **Free** | 38424 (37.5 KB) | ✅ 正常 | 可用内存充足 |
| **Min** | 21088 (20.6 KB) | ⚠️ 警告 | 历史最低接近阈值 |
| **MaxAlloc** | 20444 (20.0 KB) | ⚠️ 警告 | MaxAlloc << Free，存在碎片化 |
| **碎片化率** | (Free - MaxAlloc) / Free = 46.8% | ⚠️ 中等 | 接近一半内存不可用 |

**结论**:
- **内存充足但碎片化**: Free=37.5KB 但 MaxAlloc=20KB
- **历史内存压力**: Min=20.6KB 接近警告阈值
- **崩溃原因**: 不是内存不足，而是指针问题（LoadProhibited + EXCVADDR=0x18）
- **建议**: 优化内存分配策略，减少碎片化

## 4.6 步骤 5：可视化调用栈

**目标**: 从下往上构建调用链，理解崩溃触发路径。

### 4.6.1 调用栈方向

```
Backtrace: 0x400ef123:0x3ffb7890 0x400f5675:0x3ffb78b0 0x400f9abc:0x3ffb78d0
           ^^^^^^^^^^^            ^^^^^^^^^^^            ^^^^^^^^^^^
           崩溃点（最内层）        调用者                  调用者的调用者
```

**阅读顺序**: 从左到右 = 从内到外 = 从崩溃点到 main()

### 4.6.2 可视化格式

**方法 1: 树状图**

```
main()
  └─→ timer_task()                    [esp_timer.c:456]
        └─→ timer_callback_wrapper()  [esp_timer.c:123]
              └─→ MyClass::processData()  [MyClass.cpp:456]  ← 崩溃点
```

**方法 2: 表格**

| 层级 | 函数 | 文件 | 行号 | 说明 |
|------|------|------|------|------|
| 0 | MyClass::processData() | MyClass.cpp | 456 | **崩溃点** |
| 1 | timer_callback_wrapper | esp_timer.c | 123 | 定时器回调包装 |
| 2 | timer_task | esp_timer.c | 456 | 定时器任务 |

**方法 3: 流程图**

```
定时器触发
  ↓
timer_task() 调度回调
  ↓
timer_callback_wrapper() 包装调用
  ↓
MyClass::processData() 处理数据
  ↓
访问成员变量（偏移 0x18）
  ↓
LoadProhibited 异常（this = NULL）
```

### 4.6.3 通用示例

**输入**: 解码后的 Backtrace

```
0x400ef123: MyClass::processData() at src/MyClass.cpp:456
0x400f5675: timer_callback_wrapper at components/esp_timer/src/esp_timer.c:123
0x400f9abc: timer_task at components/esp_timer/src/esp_timer.c:456
```

**输出**: 调用链可视化

```
调用链（从外到内）:
┌─────────────────────────────────────────────────────────┐
│ 3. timer_task()                                         │
│    → 定时器任务主循环                                     │
│    → 文件: esp_timer.c:456                              │
├─────────────────────────────────────────────────────────┤
│ 2. timer_callback_wrapper()                             │
│    → 定时器回调包装函数                                   │
│    → 文件: esp_timer.c:123                              │
├─────────────────────────────────────────────────────────┤
│ 1. MyClass::processData()  ← 崩溃点                     │
│    → 处理数据的成员函数                                   │
│    → 文件: MyClass.cpp:456                              │
│    → 访问成员变量（偏移 0x18）时崩溃                      │
└─────────────────────────────────────────────────────────┘

触发路径:
定时器触发 → timer_task → timer_callback_wrapper → MyClass::processData → 访问 this->member (偏移 0x18) → LoadProhibited
```

## 4.7 步骤 6：定位根本原因

**目标**: 结合异常类型、调用栈、寄存器、内存状态，推断根本原因。

### 4.7.1 分析框架

```
1. 确定异常类型（参考 [3.1 节](#31-硬件异常表)）
2. 分析 EXCVADDR（参考 [4.4.2 节](#442-excvaddr-分析)）
3. 检查调用栈特征（参考 [3.4.2 节](#342-根据调用栈特征分类)）
4. 评估内存状态（参考 [4.5.2 节](#452-诊断规则)）
5. 匹配崩溃模式（参考 [5.4 节](#54-模式识别决策树)）
6. 推断根本原因
7. 提出修复建议
```

### 4.7.2 推理技巧

**技巧 1: 从 EXCVADDR 推断指针状态**

| EXCVADDR | 推断 | 验证方法 |
|----------|------|---------|
| 0x00000000 | 直接解引用 NULL | 检查 A2 寄存器（this 指针） |
| 0x00000018 | NULL->member (偏移 24) | 检查结构体定义，确认成员偏移 |
| 0x3fxxxxxx | 访问已释放内存 | 检查对象生命周期 |

**技巧 2: 从调用栈推断触发场景**

| 调用栈特征 | 推断 | 验证方法 |
|-----------|------|---------|
| timer_callback | 定时器触发 | 检查定时器生命周期 |
| operator new[] | 内存分配 | 检查 Free/MaxAlloc |
| WiFiUDP::parsePacket | 网络接收 | 检查缓冲区大小 |

**技巧 3: 从寄存器推断函数参数**

| 寄存器 | 含义 | 示例 |
|--------|------|------|
| A2 | 第 1 个参数（C++ this） | A2=0x00000000 → this=NULL |
| A3 | 第 2 个参数 | A3=0x3ffb5678 → 有效指针 |
| A4 | 第 3 个参数 | A4=0x00000001 → 布尔值 true |

### 4.7.3 通用示例

**综合分析**:

**输入**: 完整崩溃信息

```
异常类型: LoadProhibited (0x1c)
PC: 0x400ef123 → MyClass::processData() at MyClass.cpp:456
EXCVADDR: 0x00000018
A2 (this): 0x00000000
调用栈: timer_callback_wrapper → MyClass::processData
内存: Free=38KB, Min=21KB, MaxAlloc=20KB
```

**推理过程**:

```
1. 异常类型: LoadProhibited → 读取无效内存
2. EXCVADDR: 0x00000018 → 空指针偏移 24 字节 → 访问成员变量
3. A2 寄存器: 0x00000000 → this 指针为 NULL
4. 调用栈: timer_callback_wrapper → 定时器回调触发
5. 内存状态: Free=38KB → 内存充足，非内存不足问题
6. 匹配模式: [5.2.3 定时器生命周期问题](#523-定时器生命周期问题)
```

**根本原因**:

```
定时器回调在对象销毁后仍然执行，访问已释放对象的成员变量。

触发链:
1. MyClass 对象创建并启动定时器
2. 对象被销毁（析构函数调用）
3. 定时器停止（ets_timer_disarm）
4. 但已调度的回调仍在队列中
5. 回调执行时使用已销毁对象的 this 指针
6. 访问成员变量（偏移 0x18）
7. LoadProhibited 异常
```

**修复建议**:

```
1. 立即修复: 在析构函数中使用 ets_timer_done() 等待回调完成
2. 防御性编程: 在回调中验证对象有效性
3. 长期优化: 迁移到 esp_timer API（更安全的生命周期管理）
```

**代码示例**:

```cpp
// 修复前
~MyClass() {
    ets_timer_disarm(&_timer);  // 只停止定时器，不等待回调完成
}

// 修复后
~MyClass() {
    ets_timer_disarm(&_timer);  // 停止定时器
    ets_timer_done(&_timer);    // 等待回调完成
}
```

## 5.1 内存相关

### 5.1.1 堆内存耗尽

**识别特征**:
- **异常类型**: std::bad_alloc（参考 [3.2.1 节](#321-c-异常)）
- **调用栈**: 包含 `operator new[]`, `malloc`, `pvPortMalloc`
- **内存状态**: Free < 10KB 或 MaxAlloc 远小于请求大小
- **日志特征**: `abort() was called` + `__cxa_throw`

**触发条件**:
- 大块内存分配（如缓冲区、数组）
- 内存泄漏导致可用内存逐渐减少
- 峰值内存使用超过堆大小

**排查方向**:

```
1. 检查内存监控日志
   □ 记录崩溃前的 Free, Min, MaxAlloc
   □ 识别内存分配失败的位置
   □ 分析内存使用趋势

2. 识别内存分配失败的位置
   □ 解码 Backtrace 找到 new/malloc 调用
   □ 检查分配的大小（通常在寄存器 A2 或 A3）
   □ 确认是否为合理的分配大小

3. 分析是否存在内存泄漏
   □ 检查是否有未释放的内存
   □ 使用 heap_caps_print_heap_info() 打印堆信息
   □ 对比启动时和崩溃前的内存使用

4. 检查是否存在大块内存分配
   □ 缓冲区大小是否合理
   □ 是否可以使用静态分配或栈分配
   □ 是否可以分批处理减少内存需求
```

**验证方法**:
```cpp
// 添加内存监控日志
void printMemoryStatus() {
    log_i("Free: %d, Min: %d, MaxAlloc: %d",
          ESP.getFreeHeap(),
          ESP.getMinFreeHeap(),
          ESP.getMaxAllocHeap());
}

// 在关键位置调用
printMemoryStatus();  // 崩溃前
```

**修复策略**: 参考 [6.3 内存优化检查清单](#63-内存优化检查清单)

### 5.1.2 栈溢出

**识别特征**:
- **异常类型**: LoadProhibited 或 StoreProhibited（参考 [3.1.1 节](#311-内存访问异常)）
- **日志特征**: `***ERROR*** A stack overflow in task <任务名>`
- **调用栈**: 深度递归或包含大量函数调用
- **寄存器**: SP (A1) 接近栈底

**触发条件**:
- 递归调用过深
- 局部变量过大（大数组、大结构体）
- 任务栈大小配置过小

**排查方向**:

```
1. 检查任务栈大小
   □ 查看任务创建时的栈大小参数
   □ 使用 uxTaskGetStackHighWaterMark() 检查剩余栈空间
   □ 对比默认栈大小和实际需求

2. 识别栈消耗大的函数
   □ 检查局部变量大小（大数组、大结构体）
   □ 检查递归调用深度
   □ 检查函数调用链深度

3. 分析递归调用
   □ 是否存在无限递归
   □ 递归深度是否可控
   □ 是否可以改为迭代实现

4. 检查栈使用情况
   □ 使用 uxTaskGetStackHighWaterMark() 监控
   □ 在关键函数入口打印栈使用
   □ 识别栈使用峰值
```

**验证方法**:
```cpp
// 检查任务栈剩余空间
UBaseType_t stackRemaining = uxTaskGetStackHighWaterMark(NULL);
log_i("Stack remaining: %d bytes", stackRemaining * sizeof(StackType_t));

// 如果 stackRemaining < 100，说明栈空间不足
```

**修复策略**:
```cpp
// 增加任务栈大小
xTaskCreate(
    taskFunction,
    "TaskName",
    8192,  // 栈大小（字节），从 4096 增加到 8192
    NULL,
    1,
    &taskHandle
);

// 或将大数组改为动态分配
// 修复前
void function() {
    uint8_t buffer[4096];  // 栈上分配 4KB
}

// 修复后
void function() {
    uint8_t* buffer = new uint8_t[4096];  // 堆上分配
    // ... 使用 buffer
    delete[] buffer;
}
```

### 5.1.3 内存碎片化

**识别特征**:
- **异常类型**: std::bad_alloc（参考 [3.2.1 节](#321-c-异常)）
- **内存状态**: MaxAlloc << Free（例如 MaxAlloc=20KB, Free=40KB）
- **触发条件**: 频繁的小块内存分配和释放

**排查方向**:

```
1. 检查内存碎片化程度
   □ 计算碎片化率: (Free - MaxAlloc) / Free
   □ 碎片化率 > 30% 表示碎片化严重
   □ 记录碎片化趋势

2. 识别碎片化来源
   □ 检查频繁的 new/delete 操作
   □ 检查不同大小的内存分配
   □ 检查内存分配和释放顺序

3. 分析内存分配模式
   □ 是否存在大小不一的分配
   □ 是否存在长期持有的小块内存
   □ 是否存在频繁的临时分配

4. 优化内存分配策略
   □ 使用内存池
   □ 使用静态缓冲区
   □ 批量分配和释放
```

**验证方法**:
```cpp
// 计算碎片化率
size_t free = ESP.getFreeHeap();
size_t maxAlloc = ESP.getMaxAllocHeap();
float fragmentation = (float)(free - maxAlloc) / free * 100;
log_i("Fragmentation: %.1f%% (Free=%d, MaxAlloc=%d)",
      fragmentation, free, maxAlloc);
```

**修复策略**: 参考 [6.3 内存优化检查清单](#63-内存优化检查清单)

### 5.1.4 野指针和悬空指针

**识别特征**:
- **异常类型**: LoadProhibited 或 StoreProhibited（参考 [3.1.1 节](#311-内存访问异常)）
- **EXCVADDR**:
  - 0x00000000 → 空指针
  - 0x00000004~0x00000020 → 空指针偏移
  - 0x3fxxxxxx → 访问已释放内存
- **调用栈**: 包含对象方法调用或指针解引用

**触发条件**:
- 使用未初始化的指针
- 使用已释放的指针（悬空指针）
- 对象销毁后仍被访问

**排查方向**:

```
1. 检查指针初始化
   □ 指针声明时是否初始化为 NULL
   □ 是否在使用前赋值
   □ 是否存在条件分支导致未初始化

2. 检查对象生命周期
   □ 对象是否已销毁
   □ 是否存在悬空引用
   □ 是否存在异步回调访问已销毁对象

3. 检查指针使用
   □ 使用前是否检查 NULL
   □ 释放后是否置为 NULL
   □ 是否存在多次释放

4. 检查异步访问
   □ 定时器回调是否访问已销毁对象
   □ 任务是否访问已销毁对象
   □ 中断处理是否访问已销毁对象
```

**验证方法**:
```cpp
// 防御性编程
if (ptr != NULL) {
    ptr->method();
}

// 释放后置空
delete ptr;
ptr = NULL;

// 智能指针（C++11）
std::shared_ptr<MyClass> ptr = std::make_shared<MyClass>();
```

**修复策略**: 参考 [6.1 防御性编程检查清单](#61-防御性编程检查清单)

## 5.2 并发相关

### 5.2.1 竞态条件

**识别特征**:
- **异常类型**: LoadProhibited, StoreProhibited, 或数据损坏
- **触发条件**: 多任务或中断同时访问共享资源
- **特征**: 不确定性崩溃（时序相关）

**排查方向**:

```
1. 识别共享资源
   □ 全局变量
   □ 静态变量
   □ 堆分配的对象
   □ 外设寄存器

2. 检查访问保护
   □ 是否使用互斥锁（Mutex）
   □ 是否使用临界区（Critical Section）
   □ 是否禁用中断

3. 分析访问时序
   □ 任务优先级
   □ 中断优先级
   □ 访问顺序

4. 检查原子操作
   □ 是否使用原子变量
   □ 是否使用原子操作函数
   □ 是否存在读-改-写竞态
```

**验证方法**:
```cpp
// 使用互斥锁保护共享资源
SemaphoreHandle_t mutex = xSemaphoreCreateMutex();

void accessSharedResource() {
    if (xSemaphoreTake(mutex, portMAX_DELAY) == pdTRUE) {
        // 访问共享资源
        sharedVariable++;
        xSemaphoreGive(mutex);
    }
}
```

### 5.2.2 死锁

**识别特征**:
- **异常类型**: WDT Timeout（看门狗超时）
- **日志特征**: `Task watchdog got triggered`
- **调用栈**: 任务阻塞在锁获取

**触发条件**:
- 循环等待锁
- 锁获取顺序不一致
- 持有锁时等待其他资源

**排查方向**:

```
1. 识别死锁任务
   □ 检查看门狗日志中的任务名
   □ 检查任务状态（Blocked）
   □ 检查任务等待的资源

2. 分析锁获取顺序
   □ 绘制锁依赖图
   □ 检查是否存在循环依赖
   □ 检查锁获取顺序是否一致

3. 检查锁持有时间
   □ 是否在持有锁时执行耗时操作
   □ 是否在持有锁时等待其他锁
   □ 是否在持有锁时调用阻塞函数

4. 检查锁释放
   □ 是否在所有路径上释放锁
   □ 是否在异常处理中释放锁
   □ 是否存在忘记释放锁的情况
```

**验证方法**:
```cpp
// 使用超时避免死锁
if (xSemaphoreTake(mutex, pdMS_TO_TICKS(1000)) == pdTRUE) {
    // 访问共享资源
    xSemaphoreGive(mutex);
} else {
    log_e("Failed to acquire mutex (timeout)");
}
```

**修复策略**:
```cpp
// 统一锁获取顺序
void function1() {
    xSemaphoreTake(mutexA, portMAX_DELAY);
    xSemaphoreTake(mutexB, portMAX_DELAY);
    // ...
    xSemaphoreGive(mutexB);
    xSemaphoreGive(mutexA);
}

void function2() {
    // 保持相同的获取顺序
    xSemaphoreTake(mutexA, portMAX_DELAY);
    xSemaphoreTake(mutexB, portMAX_DELAY);
    // ...
    xSemaphoreGive(mutexB);
    xSemaphoreGive(mutexA);
}
```

### 5.2.3 定时器生命周期问题

**识别特征**:
- **异常类型**: LoadProhibited（参考 [3.1.1 节](#311-内存访问异常)）
- **EXCVADDR**: 0x00000000~0x00000020（空指针偏移）
- **调用栈**: 包含 `timer_callback`, `ets_timer_*`, `esp_timer_*`
- **寄存器**: A2 (this) = 0x00000000

**触发条件**:wwwww
- 对象销毁后定时器回调仍执行
- 定时器停止但已调度的回调仍在队列中
- 定时器回调访问已释放的对象

**排查方向**:

```
1. 检查定时器生命周期
   □ 定时器何时启动
   □ 定时器何时停止
   □ 对象何时销毁

2. 检查定时器停止逻辑
   □ 是否调用 ets_timer_disarm() 或 esp_timer_stop()
   □ 是否调用 ets_timer_done() 等待回调完成
   □ 是否在析构函数中停止定时器

3. 检查回调函数
   □ 回调是否验证对象有效性
   □ 回调是否使用 this 指针
   □ 回调是否访问成员变量

4. 检查时序
   □ 停止定时器和销毁对象的顺序
   □ 回调执行和对象销毁的时序
   □ 是否存在竞态条件
```

**验证方法**:
```cpp
// 在回调中验证对象有效性
static void timerCallback(void* arg) {
    MyClass* obj = static_cast<MyClass*>(arg);
    if (obj == NULL || !obj->isValid()) {
        return;  // 对象已销毁，直接返回
    }
    obj->process();
}
```

**修复策略**:
```cpp
// 修复前
~MyClass() {
    ets_timer_disarm(&_timer);  // 只停止定时器
}

// 修复后
~MyClass() {
    ets_timer_disarm(&_timer);  // 停止定时器
    ets_timer_done(&_timer);    // 等待回调完成
}

// 或使用 esp_timer（推荐）
~MyClass() {
    if (_timer != NULL) {
        esp_timer_stop(_timer);
        esp_timer_delete(_timer);
        _timer = NULL;
    }
}
```

### 5.4.1 基于异常类型的决策树

```
  │

  │     ├─→ EXCVADDR = 0x00000004~0x00000020
  │     │     ├─→ 调用栈包含 timer_callback

  │     │     └─→ 其他
  │     │           └─→ 空指针偏移 [5.1.4](#514-野指针和悬空指针)
  │     │
  │     ├─→ EXCVADDR = 0x3fxxxxxx
  │     │     └─→ 访问已释放内存 [5.1.4](#514-野指针和悬空指针)
  │     │
  │     └─→ 其他
  │           └─→ 访问无效地址 [5.1.4](#514-野指针和悬空指针)
  │
  ├─→ std::bad_alloc
  │     ├─→ Free < 10KB
  │     │     └─→ 堆内存耗尽 [5.1.1](#511-堆内存耗尽)
  │     │
  │     └─→ MaxAlloc << Free
  │           └─→ 内存碎片化 [5.1.3](#513-内存碎片化)
  │
  ├─→ Stack Overflow
  │     └─→ 栈溢出 [5.1.2](#512-栈溢出)
  │
  ├─→ WDT Timeout
  │     ├─→ 任务阻塞在锁获取
  │     │     └─→ 死锁 [5.2.2](#522-死锁)
  │     │
  │     └─→ 任务执行耗时操作
  │           └─→ 看门狗超时（优化任务）
  │
  └─→ 其他
        └─→ 查表 [3.3 节](#33-exccause-完整对照表)
```

### 5.4.2 基于调用栈的决策树

```
调用栈特征
  │
  ├─→ operator new[] / malloc
  │     ├─→ Free < 10KB
  │     │     └─→ 堆内存耗尽 [5.1.1](#511-堆内存耗尽)
```

```cpp
    SemaphoreHandle_t _writeLock;

public:
    RWLock() {
        _mutex = xSemaphoreCreateMutex();
        _writeLock = xSemaphoreCreateMutex();
    }

        _readers++;
        if (_readers == 1) {

        }
        xSemaphoreGive(_mutex);

        }
        xSemaphoreGive(_mutex);
    }

    void writeUnlock() {
```

#### 案例 3：SSDP 定时器竞态条件

**问题描述**:
- ESP32 在文件传输测试期间发生 1 次崩溃
- 崩溃时间：2026-02-01 14:32:40
- 运行时长：约 5 小时 56 分钟

**关键发现**:
- 异常类型：LoadProhibited (EXCVADDR: 0x00000018)
- 崩溃位置：SSDPClass::_onTimerStatic() at ESP32SSDP.cpp:456
- 寄存器：A2 (this) = 0x00000000
- 根本原因：定时器回调在对象销毁后仍执行，访问已释放对象的成员变量

**修复方案**:
- 在析构函数中使用 ets_timer_done() 等待回调完成
- 在回调函数中验证指针有效性
- 迁移到 esp_timer API（更安全的生命周期管理）

**学习要点**:
- 如何分析 LoadProhibited 异常
- 如何识别空指针偏移（EXCVADDR = 0x18）
- 如何分析定时器生命周期问题
- 如何修复定时器竞态条件
